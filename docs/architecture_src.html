GlucoTwin — System Architecture

Patient-specific digital twin for Type 2 Diabetes that fuses EHR + wearable streams to forecast glucose spikes (>180 mg/dL) 2 hours ahead
1 · Data streams (synthetic, DPDP/HIPAA-safe)
Static / historical — EHRDemographics, ICD-10 diagnoses (E11.9, R73.03, I10), LOINC labs (HbA1c, FPG, fasting insulin, lipids, eGFR), medications, genetic markers (TCF7L2, KCNQ1, FTO)
Synthea-style generator · FHIR R4 bundles
Dynamic / real-time — wearablesCGM glucose (5-min), heart rate, HRV (RMSSD), steps, sleep stages (W/L/D/R)
Apple Health / Google Fit / Libre-like schema
Patient appMeal log (incomplete, noisy carb estimates)
Ingestion & interoperabilityFHIR R4 adapter (ABDM-ready) · 5-min resampling · unit harmonisation · data-quality checks
Swap-in: MIMIC-IV, Synthea, OhioT1DM

2 · Digital twin engine (one virtual patient per patient)
MMechanistic core — extended Bergman minimal model Glucose–insulin kinetics + 2-compartment gut absorption + exercise uptake; sleep modulates insulin sensitivity
dG/dt = −(SG + X + E)·G + SG·Gb + Ra/V    dX/dt = −p₂X + p₂SI(I − Ib)
dI/dt = −n(I − Ib) + γ·(G − h)⁺    Ra = f·kabs·Q₂    dE/dt = −E/τ + kex·activity
1InitialiseEHR → prior SI (HOMA-IR, BMI), β-cell γ (diagnosis, TCF7L2/KCNQ1, sulfonylurea/DPP-4i), Gb (FPG)
2Calibrate3 onboarding days · MAP grid search on SI, γ · robust Huber loss vs CGM · Gb from night CGM
3Synchronise (every 5 min)State observer pulls virtual G to CGM · unlogged-meal detector injects carbs into gut state
4Forecast (every 15 min)Run twin 2 h ahead: "no further meal" and "habitual routine" (learned meal-time profile)
5What-if simulationCounterfactuals from the live twin state: dinner carbs −25/−50%, post-meal walk 15/30 min, short sleep, missed metformin → 24-h glucose curve, peak, minutes >180, TIR
Hybrid ML risk layer — gradient-boosted trees (scikit-learn HistGradientBoosting) 58 fused features: CGM dynamics · HR/HRV/steps/sleep · meal log & time context · EHR · twin forecasts & personalised parameters
Output: P(CGM > 180 within 120 min) · alert threshold set on training patients · patient-level hold-out evaluation · ablation M1→M4 · group explanations (log-odds)
↻ continuous loop: new CGM / wearable sample → synchronise → forecast → risk
